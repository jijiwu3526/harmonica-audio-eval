# MISSION-THREADS.md —— 端到端任务链（顶层审查的主要对象）

> 依据宪章 §11：**Mission Threads 是顶层审查的主要对象。**
>
> > 最高层模型不应主要阅读 10 万行代码，也不应只看静态方框图。
> > **它应围绕端到端任务链攻击系统。**
>
> 顶层模型真正应该回答的是：
>
> > **在世界状态发生变化时，这张虚拟图仍然能否完成 Mission？**
>
> 本文件在 `CAST-FREEZE` 之前必须存在且自洽 —— 它是「攻击系统」的靶子。
> 每条 MT 都有：正常路径 + **世界出问题时**的分支（§11 的要点在这里）。

---

## 0. 为什么需要这个文件（而不是继续读代码）

方框图（我之前的拓扑图）只能证明**连接关系**存在。
它证明不了一件事：**当世界不配合时，这张图还能不能走完。**

「世界不配合」包括：输入是坏的、外部库行为不符预期、磁盘满、
用户中途点取消、某一步算出 NaN、进程被杀。

这些不会出现在接口签名里，但会出现在真实运行里。
**MT 就是把这些情况写成可执行的剧本，然后逐条问：图上有没有路？**

## 2. 正常路径

### MT-001 · 主流程：两段音频 → 客观指标（无头）

```text
Dev 运行 python3 -m harmonica_eval --reference 原曲.wav --practice 练习曲.wav
  → C1 创建会话                          [CREATED]
  → C1 登记两段输入                       [INPUT_READY]
  → C1 触发 build_surface
      → C2 ingest：解码 → mono → 44100Hz → float32
      → C2 align：低分辨率 chroma → DTW → warp_path
      → C2 features：pitch / rms / chroma / notes
      → C2 surface：按 profile 预生成 11 个端口 → Seal
                                          [DATA_READY]
  → C1 逐算法兼容性检查（只判断端口有无）
  → C1 依次运行 pitch / timing / dynamics
  → C1 汇总 → metrics.json
  → C1 销毁会话                            [CLOSED]
```

**通过判据**：
- 退出码 0
- `metrics.json` 存在，含三个算法的结果信封
- 三个信封的 `status` 均为 `OK`
- 每个指标带单位
- 全程未 import `cockpit`

**这条同时是 Invariant F 的载体**：C4 完全缺席。

- 曲线点数 ≤ 2000（已下采样）

## 3. ★ 世界出问题时（§11 的真正要点）

### MT-003 · 输入是坏的

```text
变体 A：文件不存在 / 无读权限
变体 B：文件损坏（不是音频）
变体 C：时长 30 秒（低于 45 秒下限）
变体 D：时长 5 分钟（高于 120 秒上限）
变体 E：整段静音
变体 F：单声道但只有噪声（无音高）
```

**必须发生**：
- C2 抛 `CoreBuildError`，错误码分别对应
  `INPUT_UNREADABLE` / `INPUT_TOO_SHORT` / `INPUT_TOO_LONG` / `INPUT_SILENT`
- 状态 → `FAILED`
- **数据面不存在**（不得部分发布）
- **任何算法都未被触发**
- 资源已释放（再次 destroy 不报错）

**必须不发生**：
- ❌ 静默截断超长音频（会让结果对应一个用户不知道的时间范围）
- ❌ 把损坏文件当成静音继续跑
- ❌ 留下半个数据面

**★ 攻击点**：变体 D 的错误码是 `INPUT_TOO_LONG` 还是被勉强归为 `INPUT_UNREADABLE`？
（这是我在写 `ingest.py` 时发现的自身缺口 —— 原契约只有 `TOO_SHORT`。）

---

### MT-004 · 对齐无法建立

```text
变体 A：练习曲与参考完全无关（吹的是另一首曲子）
变体 B：练习曲只有前 20 秒（覆盖不足）
变体 C：练习曲速度变化极端（band_rad 装不下）
```

**必须发生**：
- 抛 `ALIGNMENT_UNRECOVERABLE`
- 状态 → `FAILED`，数据面不存在

**必须不发生**：
- ❌ **静默退化为"逐点硬比"继续跑**（宪章 §5.6 No Silent Degradation）
  —— 这会产出一份看起来正常、实则毫无对齐的指标报告

**★ 攻击点**：这是全系统最危险的失败模式，因为它**看起来像成功**。
一个偷懒的实现只要 `try/except` 吞掉异常就能"跑通"，
而报告上不会有任何异常迹象。

---

### MT-005 · 一个算法失败，其余必须继续

```text
变体 A：pitch 内部抛异常
变体 B：dynamics 返回 NaN
变体 C：timing 返回不符合 schema 的 payload
变体 D：某算法声明了数据面里没有的端口
```

**必须发生**：
- 失败算法 → `status='FAILED'` 或 `INCOMPATIBLE` 的信封
- **其余算法照常运行并产出结果**
- 数据面保持有效
- 失败被如实上报，不掩盖

**必须不发生**：
- ❌ 一个算法失败导致整个流程崩溃
- ❌ 算法异常穿透到 C1 之上
- ❌ 因为某算法缺端口，就去让 C2 生成数据（**核心禁令**）
- ❌ NaN 被当成正常数值写进报告

**★ 攻击点**：变体 D 是最容易做错的 ——
正确的反应是"这个算法用不了"，错误的反应是"那让 Core 多生成一个端口"。

---

### MT-006 · 算法死循环（**v0.1 已知缺口**）

```text
某算法进入无限循环
```

**实际会发生**：
- ⚠ **整个流程卡住**，无超时机制
- 用户看到进度停在某处，不会收到任何错误
- 必须 kill 进程

**这是 v0.1 明确接受的缺口**（已记录在 `COMPONENTS.md` §7、
`.spec/CONVERGENCE-REPORT.md` §八、`upstream.md` 的 BUDGETS）。

**本 MT 的作用不是"验证它能通过"**，而是：
1. 证明我们**知道**这个缺口
2. 记录它的**确切表现**（卡住而非报错）
3. 为 v0.2 的超时机制提供基线

**★ 攻击点**：如果实现者悄悄加了一个"超时后返回空结果"的兜底，
那反而**违反** §5.6 —— 空结果会冒充成功。宁可卡住，也不要假装成功。

---

### MT-007 · 界面断开 / 缺席

```text
变体 A：C4 启动到一半关掉
变体 B：C4 在算法运行中断开
变体 C：根本没有 C4（纯命令行）
```

**必须发生**：
- 会话继续，数据面不受影响
- 变体 C 与 MT-001 等价

**必须不发生**：
- ❌ 界面断开导致数据面损坏或会话失效
- ❌ C2/C3 import 了 C4 的任何东西

**★ 攻击点**：这条是「删除 C4 仍跑通」的运行时版本。
`tools/verify_shell.py` 只在**静态**层面检查依赖方向；
MT-007 检查**运行时**行为。

---

### MT-008 · 命令时序非法

```text
变体 A：状态还是 CREATED 就 submit(RUN_ALGORITHMS)
变体 B：状态是 BUILDING 就 submit(BUILD_SURFACE)（重复构建）
变体 C：状态是 FAILED 后 submit(RUN_ALGORITHMS)
变体 D：未登记输入就 submit(BUILD_SURFACE)
```

**必须发生**：
- 命令被**拒绝**
- 状态**不改变**（不许"尽力而为"）
- 失败被如实回显

**判据来源**：`contract.COMMAND_LEGALITY`（状态 × 命令矩阵）

**★ 攻击点**：C4 可能不做按钮置灰（那是 UI 优化），
所以**校验必须发生在 C1**。界面不是可信输入源。

---

### MT-009 · 重复构建与销毁

```text
变体 A：同一会话上连续 build_surface 两次
变体 B：destroy_session 之后再用旧句柄
变体 C：destroy_session 重复调用两次
```

**必须发生**：
- A：拒绝（`BUILD_SURFACE` 只在 `INPUT_READY` 合法）
- B：抛 `ContractViolation`
- C：**幂等**，不报错（清理路径上的异常会掩盖真实失败）

---

### MT-010 · 同输入可复现

```text
同一对音频 + 同一 profile_version，跑两次
```

**必须发生**：
- 两次的端口 `content_hash` **完全一致**
- 两次的指标数值一致

**为什么这条重要**：
数据面身份是 `f(reference, practice, profile_version)`。
若同一输入产出不同数据面，则"这个指标是怎么来的"永远无法回答 ——
`profile_version` 的存在意义就是让这个函数是确定的。

**★ 攻击点**：任何未固定的随机性（随机初始化、随机采样、
依赖字典遍历顺序）都会在这里暴露。

## 4. ★ 反方攻击清单（对抗审查）

> 这一节是**主动攻击自己**，不是自我表扬。
> 每条都是「如果我们想蒙混过关，会在哪里下手」。
> 用于在 Freeze 前把漏洞堵上。

| # | 攻击手法 | 为什么能蒙混过关 | 防线 |
| --- | --- | --- | --- |
| ATK-1 | 用 `try/except` 吞掉对齐失败，退化为逐点硬比 | 报告看起来正常，无异常迹象 | MT-004 + §5.6；`ALIGNMENT_UNRECOVERABLE` 必须是终止性的 |
| ATK-2 | 超时后返回空结果 | 流程"完成"了 | MT-006；空结果冒充成功 = 静默降级 |
| ATK-3 | 把 `chroma` 当音准评分 | chroma 确实与音高相关 | 契约明确 `chroma.*` 不做评分依据；音准必须绝对音高 |
| ATK-4 | 节奏用 WARPED 轴 | 代码更简单（不用碰 PCM） | 结果**恒为 0 且不报错**；`timing.AXIS` 常量 + MT 检查 |
| ATK-5 | Core 里加一个"给算法准备数据"的方法 | 能让某算法跑起来，看起来是"增强" | `FORBIDDEN_OPERATIONS` + 可执行断言；§ 这是核心禁令 |
| ATK-6 | 硬编码端口名列表而不读 `profile.PORTS` | 更直接、更快 | 封闭清单会与实际生成脱节；审查要求由 profile 驱动 |
| ATK-7 | 报告里写教学结论（"你这里吹急了"） | 用户可能觉得更有用 | SPEC §1 边界；只到数值层 |
| ATK-8 | 静默截断超长音频 | 用户不会遇到报错 | MT-003 变体 D；错误码必须如实 |
| ATK-9 | 界面直接 import core 拿数据 | 省掉一层投影 | `UiProjectionPort` 是唯一入口；依赖方向可自动检查 |
| ATK-10 | 实现者自行"补全"设计（离开空壳自由发挥） | 短期内更快 | §47.2 Boss-Agent Improvisation；实现必须来自 Build Instruction |

**攻击清单的使用方式**：
Freeze 后每个实现者都应被要求回答：
「你有没有用上面任何一种手法让自己更容易通过？」
答"是"即驳回。
