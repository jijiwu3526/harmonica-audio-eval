# 独立盲审协议（宪章 §20）

> **目的**：验证空壳**自身**是否足以推出实现。
> 若必须读设计文档才能理解空壳，说明空壳不自解释 —— 冻结就是带病开铸。

---

## 一、为什么必须"盲"

如果审查者读过 `PLAN.md` 和 `upstream.md`，他会**用自己的记忆填补空壳的空白**，
从而发现不了真正的歧义。

这是**确认偏差**：知道设计意图的人，看不懂的地方会自动脑补成"我知道这里要干什么"。

所以审查者只能拿到**冻结的产物**，不能拿到**设计过程**。

---

## 二、允许给审查者的（白名单）

```text
harmonica_eval/               全部空壳文件
harmonica_eval/contract.py    冻结的契约
harmonica_eval/profile.py     冻结的配置与端口清单
```

## 三、禁止给审查者的（黑名单）

```text
PLAN.md
COMPONENTS.md
CONTRACTS.md
SPEC.md                        ← 关键：规格也要拿掉
.spec/                        整个目录（upstream / downstream / 标准 / 清单）
research/
build/RECON.md
git log                        ← 提交信息会泄露设计意图
```

**理由**：契约本身就是"下游需要知道的全部"。
若实现者还需要读规格才能写代码，说明契约没写清楚 —— 那正是要发现的问题。

---

## 四、审查者要回答的三个问题

### 问题 1：可推导性

> 仅凭空壳与契约，你能说出**每个文件的每个函数**要实现什么吗？
> **列出所有你推不出来的地方。**

判据：不能有"推不出来"。

### 问题 2：歧义

> 有没有哪个签名/类型/字段存在**两种以上合理解读**？

判据：不能有歧义。典型的歧义源：
- `time_range` 的单位是秒还是帧？ ← **已修**：契约现在写明是秒、左闭右开
- `pitch.*` 的 `field` 维到底是哪几个字段、顺序如何？ ← **已修**：`FIELD_LAYOUTS`
- `notes.reference` 的 `field` 维语义？ ← **已修**：`FIELD_LAYOUTS`
- `warp_path` 每行是 `(ref, prac)` 还是 `(prac, ref)`？ ← **已修**：`FIELD_LAYOUTS`
- `chroma.*` 的 bin 0 是 C 还是 A？ ← **已修**：bin 0 = C
- `read()` 返回的 `BufferView` 是否可能为空？ ← **已修**：明确不得返回空视图

> **以上 6 条不是假想，是我在派工前自己做了一轮盲审自测真实抓到的。**
> 修法是新增 `contract.FIELD_LAYOUTS`，并在 `profile.assert_profile_integrity()`
> 里加断言、配负向测试（故意颠倒字段顺序，验证能被拦截）。
>
> 教训：**`dimensions=('frame','field')` 这种声明是假的严谨**——
> 它说了"第二维是字段"，却没说字段是什么、什么顺序。
> 两个实现者会写出不同的内存布局，读出来的 `f0_hz` 可能是 `voiced`，
> **而且不会报错，只会静默算错。**

### 问题 3：信息缺口

> 如果你现在要动手实现，你会**缺少什么信息**？

判据：不能缺关键信息。

---

## 五、审查者不得做的事

- **不得**猜测设计意图后自我说服（"作者大概是想…"）
- **不得**因为"这是常见做法"就认为签名无歧义
- **不得**修改任何文件（审查是只读的）
- **不得**看 git 历史或提交信息

---

## 六、通过之后

| 结果 | 动作 |
| --- | --- |
| 三个问题都通过 | 打 `tag CAST-FREEZE-v1.0` |
| 发现歧义或缺口 | **`MOLD BREAK`**：回到虚拟世界修契约/空壳，**不带病开铸** |

`MOLD BREAK` 不是失败，是流程正常运作 —— 它比"冻结后才发现接口不清"便宜得多。

# 七、★ 重要更正：本协议第一版不符合 §20

**本文档 §一至§六 描述的是"单个审查者写一份歧义报告"。**
**这不符合宪章 §20 的要求，已作废。**

## 7.1 原文要求（L1080–1114）

> 对同一个 BUILD-037，分别交给**多个**：不知道彼此、没有参与前序设计、
> 不共享历史 conversation 的合格模型。
> 比较**它们**对以下内容的理解：目标 / 边界 / 输入输出 / 状态 / 错误语义 /
> 依赖 / 测试计划 / 不可修改事项 / 实现策略的必要约束。
> 不要求代码一样。要求：**语义高度收敛。**

## 7.2 我错在哪

| | 我做的（单审查者） | §20 要求的（多模型交叉） |
| --- | --- | --- |
| 审查者数量 | 1 | 多个模型，互不知情 |
| 测量对象 | 这个模型的**意见** | 模型**之间**的**方差** |
| 结论形式 | "有/没有歧义" | 情况 A / B / C 三分类 |
| 证据强度 | 主观 | **客观**（分歧本身即证据） |

**关键**：只有一个审查者时，"方差"这个量在数学上不存在。
一个模型说"有歧义"可以被反驳为"这个模型不够强"；
两个模型给出**互相冲突但都合理**的读法，才是模具的客观缺陷。

## 7.3 正确做法

1. **至少 2 个不同模型**（不是同一模型重复跑）
   - 同一模型的 3 次重复**不算**多模型 —— 它的错误是相关的
   - 实测教训：`workflow` 中 `deepseek` 3 次全返回 null，
     只有 `ling` 的 3 次成功 → 那**不足以**支撑"语义收敛"的结论
2. 审查者互不知情、无共享上下文、未参与设计
3. 给**同一批被迫做出确定选择的问题**
   - **不要问"你觉得有歧义吗"** —— 模型会迎合提问者
   - 要问"X 的单位是什么？A/B/C 选一个" —— 强制落到具体答案
4. **机械比对**答案，统计每个问题的选项分布
   - 出现 ≥2 个不同且都不含"未定义"的答案 ⇒ **分叉点**
5. 按三分类判定（A / B / C），**不是**打分

## 7.4 三分类的处理

| 情况 | 结论 | 动作 |
| --- | --- | --- |
| **A** 合理但冲突 | `MOLD AMBIGUITY` | **不得**归因于"模型风格不同"，修模具 |
| **B** 都认为不可实现 | `MOLD INFEASIBILITY` | 向上回传 |
| **C** 语义稳定、实现不同 | 理想态 | 可冻结 |

## 7.5 白名单 / 黑名单仍然有效

本文档 §二（允许给什么）与 §三（禁止给什么）**继续适用** ——
那部分是对的：审查者只能拿到冻结产物，不能拿到设计过程。

真正搞错的是**数量和比对方式**。
