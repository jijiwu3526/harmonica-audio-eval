# 独立盲审协议（宪章 §20）

> **目的**：验证空壳**自身**是否足以推出实现。
> 若必须读设计文档才能理解空壳，说明空壳不自解释 —— 冻结就是带病开铸。

---

## 一、为什么必须"盲"

如果审查者读过 `PLAN.md` 和 `upstream.md`，他会**用自己的记忆填补空壳的空白**，
从而发现不了真正的歧义。

这是**确认偏差**：知道设计意图的人，看不懂的地方会自动脑补成"我知道这里要干什么"。

所以审查者只能拿到**冻结的产物**，不能拿到**设计过程**。

---

## 二、允许给审查者的（白名单）

```text
harmonica_eval/               全部空壳文件
harmonica_eval/contract.py    冻结的契约
harmonica_eval/profile.py     冻结的配置与端口清单
```

## 三、禁止给审查者的（黑名单）

```text
PLAN.md
COMPONENTS.md
CONTRACTS.md
SPEC.md                        ← 关键：规格也要拿掉
.spec/                        整个目录（upstream / downstream / 标准 / 清单）
research/
build/RECON.md
git log                        ← 提交信息会泄露设计意图
```

**理由**：契约本身就是"下游需要知道的全部"。
若实现者还需要读规格才能写代码，说明契约没写清楚 —— 那正是要发现的问题。

---

## 四、审查者要回答的三个问题

### 问题 1：可推导性

> 仅凭空壳与契约，你能说出**每个文件的每个函数**要实现什么吗？
> **列出所有你推不出来的地方。**

判据：不能有"推不出来"。

### 问题 2：歧义

> 有没有哪个签名/类型/字段存在**两种以上合理解读**？

判据：不能有歧义。典型的歧义源：
- `time_range` 的单位是秒还是帧？
- `pitch.*` 的 `field` 维到底是哪几个字段、顺序如何？
- `notes.reference` 的 `field` 维语义？
- `warp_path` 每行是 `(ref, prac)` 还是 `(prac, ref)`？
- `read()` 返回的 `BufferView` 是否可能为空？

### 问题 3：信息缺口

> 如果你现在要动手实现，你会**缺少什么信息**？

判据：不能缺关键信息。

---

## 五、审查者不得做的事

- **不得**猜测设计意图后自我说服（"作者大概是想…"）
- **不得**因为"这是常见做法"就认为签名无歧义
- **不得**修改任何文件（审查是只读的）
- **不得**看 git 历史或提交信息

---

## 六、通过之后

| 结果 | 动作 |
| --- | --- |
| 三个问题都通过 | 打 `tag CAST-FREEZE-v1.0` |
| 发现歧义或缺口 | **`MOLD BREAK`**：回到虚拟世界修契约/空壳，**不带病开铸** |

`MOLD BREAK` 不是失败，是流程正常运作 —— 它比"冻结后才发现接口不清"便宜得多。
