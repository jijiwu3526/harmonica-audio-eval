# Build Instruction 模板（§19 Build Packet / §22 质量评定）

> 本文件是模板，不是 Build Instruction 本身。
> 每份 `FILE-0NN-v1.md` 按此结构撰写。

---

## 为什么需要这份模板

§19 的判据是 **Agent Interchangeability**：

> 一个**没参与前期设计**的合格 Agent，拿到这份指令后，
> 应当产出与设计意图一致的实现，而**不需要自己发明上层设计**。

§22 把「Build Instruction 仍要求 Coding Agent 自行做上层设计」
列为**硬失败**。前两轮 §20 盲审反复暴露的正是这一条：
实现者被迫自己发明阈值、自己选口径。

故本书写的铁律：**每一个"你可以自由决定"的字眼，都必须先被问一遍
"这个决定真的属于实现层吗？"** 若是设计决定，就必须在此写死。

## 4 · 你要实现什么（行为规格）

对每个公开符号给出：

### `函数名(参数) -> 返回`

- **输入**：类型、取值域、单位、空值处理
- **输出**：类型、形状、单位、时间基准
- **算法口径**：★ 必须写到"另一个实现者能复现同一数字"的程度
- **边界**：空输入 / 单元素 / 极值 / NaN / inf 各返回什么
- **不变量**：返回后必须为真的性质

> ★ 凡涉及数值口径（中位数用什么 / 阈值多少 / 容差多少 /
> 单位怎么换），**必须在此写死**，不得留给实现者"自行选择"。
> 若上游契约已冻结该值，**引用其常量名**，不要抄数字。

## 10 · ★ 何时必须停止并上报（§22 硬失败对策）

**以下情况必须停止，提交 `MOLD BREAK`，不得自行设计：**

1. 你发现本文件**需要做上层设计**才能实现
   （例如：需要决定一个新阈值 / 新口径 / 新端口 / 新错误码）
2. 本文件与任何上游工件**冲突**
3. 你需要的依赖**不在 §3 清单里**
4. §4 的行为规格**不足以确定唯一实现**
5. 你认为 §4 的规格本身**是错的**

**上报格式**（宪章 §37 Gate Challenge）：
```
GATE CHALLENGE
- 相关 Requirement：
- 相关 Build Instruction 章节：
- 实际需要 vs 规格给出：
- 为什么冲突：
- 复现证据：
- 建议的上游处理位置：
```

**绝对禁止**：
- 先做一个"能跑的 workaround"，以后再说（§38 明文禁止）
- 自行在代码里加一个"合理的"默认值把冲突掩盖过去
- 静默缩小范围（"这个分支我先不实现"）

## 撰写时的自检（§22 的 14 维）

写完后逐条自问：

| 维度 | 自问 |
| --- | --- |
| 意图保真 | 能否从本文追溯到 Product Intent？ |
| 角色纯洁 | 有没有让实现者做不属于他层级的事？ |
| 范围闭合 | §3 的依赖清单是否**穷举**？ |
| 接口完整 | §4 是否覆盖全部公开符号？ |
| 依赖确定 | 版本是否锁定？ |
| 状态完整 | 状态机/生命周期是否说清？ |
| 失败完整 | §5 是否覆盖所有失败路径？ |
| 构建充分 | 能否照着写出代码而**不问一个设计问题**？ |
| 验证充分 | §8 的判据是否可机械判定？ |
| 歧义控制 | 有没有"可以/建议/通常"这类词？ |
| 可追溯 | 每条规格是否指向上游工件？ |
| 升级清晰 | §10 是否说清何时停？ |
| 无未决冲突 | 有没有两条规格互斥？ |
| 无重大语义分叉 | 两个独立实现者会不会得到不同语义？ |
