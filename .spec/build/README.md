# .spec/build/ —— 注入指令目录（L3 阶段）

> **当前状态：目录已就位，指令待生成。**

---

## 为什么这里是空的

每个空壳文件的铭牌里都写着：

```text
BUILD-INSTRUCTION: .spec/build/FILE-0NN-v1.md
```

这是**指向未来的引用**，指向该文件的**实现注入指令**。

但 `CAST-FREEZE` 之前**不该**有注入指令，因为：

| 顺序 | 动作 | 理由 |
| --- | --- | --- |
| 1 | 空壳冻结 | 接口定了，行为契约成立 |
| 2 | 独立盲审 | 验证空壳自解释 |
| 3 | 打 `CAST-FREEZE-v1.0` | 虚拟世界收敛 |
| **4** | **生成 Build Instruction** | 此时才能写"怎么实现" |
| 5 | L3 注入代码 | 真实世界建造 |

如果在第 1 步就写注入指令，等于**在接口还没审过的时候就写实现方案** ——
一旦审查发现接口有歧义，全部注入指令作废。

## 冻结时如何处理这个悬空引用

悬空引用是**已知的、被接受的**，不是遗漏。理由：

- 它指明的是**未来会存在**的产物，不是现在应该存在的
- 盲审者只被要求"推出要实现什么"，不被要求"找到注入指令文件"
- 冻结后立刻按顺序生成，悬空期只有一步

**但必须记录在案**，避免后人误以为文件丢了。

## 冻结后生成方式

每个文件一份，`FILE-0NN-v1.md`，内容结构：

```text
FILE-ID / 目标文件路径
契约来源（contract.py 的哪些类型、profile.py 的哪些常量）
行为规格（输入→输出，含边界与失败）
必须满足的不变量（从 MUST / MUST NOT 抄下来）
验证方法（怎么证明注入后仍满足虚拟件的保证 —— 宪章 §35 Real ⊑ Virtual）
禁止事项（该文件专属的越界）
```

**一次只注入一个文件**，注入后立刻跑该文件的验证。
不要批量注入 —— 批量注入会让失败无法归因。
