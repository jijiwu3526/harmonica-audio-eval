◆

为什么"编译编排"放在 C1 而不是 C2

如果放 C2，那"Core 完全不知道算法存在"就只是纪律，靠自觉维持。 放 C1 后它成了结构事实——可以用依赖方向自动检查（Core 不许 import 算法目录）。 这是我唯一与你原稿不同的判断，请重点看。

三 · 那个假冲突是怎么消失的

上一版我把它包装成一个难题： "教义要求 Core 每次全量生成所有数据，但手机内存扛不住，怎么办？"

这个难题本身是错的。因为"全量生成"这句话里， "全量"是相对于冻结的 profile 而言的，不是相对于想象的。

错误理解

算法将来可能要 CQT / Mel / Chroma，所以 Core 现在就得都生成 → 内存爆炸

这等于让"想象中的未来算法"去改模具——正是宪章禁止的反模式。

正确理解

profile 定义多少，就全量生成多少。算法想要别的， 从始终存在的 aligned PCM 自己算。

于是"全量生成"与"手机跑得动"不再对立——它变成一个普通的规模取舍。

逃生口：aligned PCM 永远存在

Core 不需要预测世界上所有算法的中间量（那是无限的）。 它只需保证两份对齐后的 PCM 常驻，任何算法都能拿它自己做特有预处理—— 但这属于算法私有加工，不得反向污染 Core。

四 · 什么叫"深组件"

你要的"降低信息熵"，落点在这里：接口极小，实现极深。 C2 是唯一核心，它内部藏了标准化、对齐、双表示实体化、数据面生成、端口存储—— 但对外只暴露 9 个操作。

◆

你的理解方向对了，但我要把话说准（这是我上面措辞太含糊）

对：确实是"Core 先把音频预先加工成几种数值表示，算法直接拿去读"。 但有两个关键点必须分清，否则会误判这个决定的分量。

① 不是"文件格式"，是同一段音频的不同数值视图

不是 wav / mp3 那种转码。是同一段时间轴上的不同数学表示： 幅度频谱（看音高）、能量包络（看节奏与气息）、CQT / Mel / chroma 等。 时间轴对齐不变，只是"看它的角度"不同。

② 这决定的是快不快，不是能不能

这点最重要：因为两份 aligned PCM 永远存在， 算法完全可以拿 PCM 自己现场算任何一个视图。 所以选"最小"不会让任何算法做不到，只会让它多花一点时间。 换句话说：profile 是预制菜，不是食材。食材永远管够。

③ 那为什么还要预加工？真正的理由是统一口径

假设音准算法自己算频谱用窗口 512，节奏算法自己算用窗口 2048—— 两者的结果就没法放在一起比了，因为"一个频谱"在系统里没有唯一定义。 Core 预加工的意义是当唯一权威： "在本系统里，幅度频谱到底指什么"只有一个答案。 省时间只是顺带的，可比性才是不可替代的。

但这暴露了一个真问题，而它有个漂亮解法

冻结定义（契约）

profile 明确写死"本系统的幅度谱 = n_fft 2048 / hop 512 / Hann"。 算法要么用这个定义，要么声明自己用了别的。 → 可比性得到保证。

推迟实体化（实现）

按需现算并缓存。用多少算多少，内存不随 profile 膨胀。 → 内存降到 ~95 MB。

七 · 深水区（想看再展开）

▸ 数据面契约给了算法什么保证

只读且不可变：Seal 之后任何角色都没有写权限。 算法只能借用缓冲，不能释放、不能修改、不能跨会话保存指针。

必须自带采样率。这不是元数据，是结果的成因： 我们在建数据集时实测到，同一段音频在 22.05 kHz 下 pYIN 会把 D5 判成 D4 （误差恰好 −1200 音分），44.1 kHz 下则正常。

必须自带时间基准：每个端口要声明自己挂在"参考时间轴"还是"归一化时间轴"上。 因为归一化会抹掉抢拍拖拍——拿它去报节奏错误是构造性错误。

兼容性检查是单向的：算法声明需要哪些端口，只用来判断"有没有"。 缺失就是"不兼容"，绝不允许反过来让 Core 去生成。这是整套设计的良心所在。

▸ 失败怎么隔离（含我还没解决的）
失败数据面其他算法
输入不可解码 / 静音不存在不启动
对齐无法建立映射不存在不启动

▸ 为什么"哈希一致"不能当验收标准

我上一版把"装 0 个算法与装 N 个算法、数据面哈希一致"当成了验收条件。 它能证明"数据面与算法无关"，但它不能作为跨实现、跨平台的验收标准—— 浮点 FFT 换个库版本或换个 CPU 架构就不会逐位相同。

真正的"模具合格"检验应该是：每个端口符合其冻结契约 （结构、维度、单位、时间基准、采样率全部可校验）。 哈希一致只是它的一种加强特例，且仅限于同一个构建。

宪章里对应的是 §35 Real ⊑ Virtual： 真实组件只需满足虚拟组件承诺的对外可观察行为，不要求内部实现相同。
