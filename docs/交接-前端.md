## 1 · 五分钟看懂

### 1.1 内核有什么

一个 Python 包 `harmonica_eval`，做一件事：**两段音频进去 → 客观数值指标出来**。

架构分四层（`COMPONENTS.md` 命名，代码里是这四个目录）：

| 层 | 目录 | 职责 | 手机界面能不能碰 |
|---|---|---|---|
| C2 核心 | `harmonica_eval/core/` | 解码 → 对齐 → 物化 12 个端口 | ★ 通过门面间接用，**不直接 import** |
| C3 插件 | `harmonica_eval/algorithms/` | 3 个算法插件（音准/节奏/力度） | 不 import |
| C1 宿主 | `harmonica_eval/host/` | 会话编排、结果投影 | **★ 这就是你的入口** |
| C4 界面 | `harmonica_eval/cockpit/` + `serve_ui.py` + `harmonica_eval_web/` | Mac 上的 React 调试界面 | 不需要移植（第 4 节） |

**内核实测状态**（我本机复跑确认的部分，标注了输入）：

```
输入 = android/app/src/main/python/ref.wav（50.0 秒 / 2205000 采样点 / 44100 Hz）
  ingest        0.0Xs   → float32 (2205000,)
  align         1.27s   → warp_path (1083, 2) int32
  build_surface 7.9s    → 12/12 端口全部产出、sealed=True
```

> ★ **你给的这组数字我逐条复现了**（见第 2 节），全部对得上。
> ★ 区别要说明：这组 shape 是 **50 秒** 的 `ref.wav`；
> **Mac 数据集那批 wav 是 72.80 秒**，所以同一份代码在那里 `warp_path` 是 `(1870, 2)`、
> `pcm.*` 是 `(3210572,)`。★ shape 依赖输入时长，★ 界面绝不能硬编码任何 shape。
>
> 「真机 11.43 秒 / 峰值 VmHWM 422 MB」「电脑 9.42 秒 / 620 MB」——**我没有真机，未复验**，
> 按交接要求直接引用。

### 1.2 界面要接什么

**一条命令序列，五步**（`harmonica_eval_web/src/api.js:30-47`，实测可用）：

```javascript
POST /command  {"kind":"RESET"}
POST /command  {"kind":"SET_REFERENCE","path":"<参考音频路径>"}
POST /command  {"kind":"SET_PRACTICE", "path":"<练习音频路径>"}
POST /command  {"kind":"BUILD_SURFACE"}          // ★ 十几秒，同步阻塞
POST /command  {"kind":"RUN_ALGORITHMS","only":["pitch","timing","dynamics"]}
```

**★ 为什么必须先 `RESET`（顺序是承重的，实测有判据守着）**：
`SET_REFERENCE` / `SET_PRACTICE` 只在 `{CREATED, INPUT_READY}` 合法，
`BUILD_SURFACE` 只在 `{INPUT_READY}` 合法。
服务启动即跑完一轮，状态恒为 `DATA_READY`，所以不先 `RESET` 会被内核拒绝并回 400。
（判据：`tests/test_cockpit_flow.py:587` `test_skipping_reset_is_rejected_by_kernel`）

**然后读状态**：

```
GET /view      → UiView 的 JSON（结果；我实测：16 scalars + 6 series + 12 port_summary）
GET /dataset   → 曲名清单 + 插件清单（我实测：10 首歌 / 70 个 wav / plugins=[pitch,timing,dynamics]）
```

> ★ **手机端这三个端点用不了**（那是 Mac 上一个 `http.server` 的）。
> 你要么在 Chaquopy 里直接调 Python 函数，要么自己起服务。★ 选哪条是第 9 节的决策点。

#### ① `warp_path` — DTW 对齐路径

```python
units="index"  dimensions=("warp_point","axis")  field_names=("reference_frame","practice_frame")
shape=(1083, 2)  int32   hop=0   sample_rate=0（与采样率无关）
```

**第 0 列 `reference_frame`**：参考侧的帧号，int32，范围 `0 … 1075`（实测）。
**第 1 列 `practice_frame`**：练习侧的帧号，int32，范围 `0 … 1075`（实测）。

**帧号怎么定义的**：帧移 = `profile.ALIGN.hop_length` = **2048 采样点**。
帧 `i` 的起始采样点 = `i × 2048`，起始秒数 = `i × 2048 / 44100 ≈ i × 0.04644` 秒。
所以帧 1075 ≈ 第 49.92 秒。

**怎么算出来的**（`core/align.py`）：
```
1. compute_alignment_features  每侧各算一遍
   scipy.signal.stft(nperseg=4096, noverlap=2048, window='hann', fs=44100)
   → 只保留 27.5 Hz – 4200 Hz（滤直流与超声）
   → 12 个 pitch-class 分箱，bin = round(12·log2(f/27.5)) mod 12   （以 A0=27.5Hz 为参考）
   → 每帧 L2 归一化（抵消整体响度，★ 只留谱形）
   ★ 合法帧数 = (n_samples - 1) // 2048，★ 末尾越过音频的补零帧被裁掉
2. compute_warp_path
   cdist 欧氏距离 → 带宽 |i/n_ref − j/n_prac| ≤ 0.25 外置 inf
   → 逐格 DP（★ 纯 Python 双重循环，★ 这是 align 慢的根因）
   → 从 (n_ref−1, n_prac−1) 贪心回溯到 (0,0)
3. assert_monotonic（第 0 列严格不回退）+ measure_coverage ≥ 0.90
```

**值域**：第 0 列单调不减，从 0 递增到 1075。行数 1083 > 1076，因为 DTW 路径
在练习侧停留时会在参考侧走多步 —— ★ **行数与两侧帧数都不相等，这不是 bug。**

**界面怎么用**：**不要**把它当曲线画（1083 个点、纯整数、看不出意义）。
它的价值是「对齐关系的存在证明」和「重算 warped PCM 的依据」。
真要可视化，★ 先把第 1 列画成「第 0 列 → 练习时刻」的映射曲线才有意义。
（`profile.py:255-257` 的 rationale 也这么说：它是「其余全部端口的生成依据」。）

#### ②③ `pcm.mapped.reference` / `pcm.mapped.practice` — 参考侧与练习侧 PCM

```python
units="amplitude"  dimensions=("sample",)  field_names=()（单维，无列）
shape=(2205000,)  float32   hop=0   sample_rate=44100
```

**单列** = 逐采样点幅度，**线性**（不是 dB），float32，实测范围 `-0.6967 … 0.7070`。

**怎么算出来的**：`core/surface.py:114-116` 的 `_forward` 是**纯转发，零计算** ——
就是把 ingest 出来的数组原样递过来。`ingest` 做过：解码 → 下混单声道 →
`resample_poly` 重采样到 44100 → float32（`core/ingest.py:16`）。

**★ 这两个端口是数据面永远存在的保证**（`contract.py:785` `CORE_REQUIRED_PORTS`）：
算法永远能拿 PCM 自己算，profile 只决定「快不快」，不决定「能不能」。

**界面怎么用**：
- ★ **画波形直接用**，但 ★ **采样率 44100、50 秒 = 220 万点**，
  手机上画 220 万个 SVG 顶点会卡死。**必须下采样**（第 9 节建议 3）。
- 练习侧与参考侧**长度可能不同**（两段独立录音）。★ 不要假设等长。

#### ④ `pcm.warped.practice` — 按 warp_path 重排后的练习侧 PCM

```python
units="amplitude"  dimensions=("sample",)  timeline_basis=WARPED   ★ 唯一在 WARPED 上的端口
shape=(2205000,)  float32
```

**单列** = 幅度，线性。实测范围 `-0.5962 … 0.6174`（与参考不同，因为重排过）。

**怎么算出来的**（`core/surface.py:119-180` `_warp_by_index`）：

```python
for 每个参考采样点 i:
    ref_frame    = min(i // 2048, n_rows - 1)      # 落到 warp_path 的第几行
    prac_frame   = warp_path[ref_frame, 1]          # 取练习侧帧号
    out[i]       = practice[prac_frame * 2048]      # 索引练习侧采样点（钳位到合法范围）
```

> ★★★ **极其重要的一条实读结论 ★★★
> ★ 这个函数名叫「warp」，但源码 docstring 写的是「**非重采样**」（`surface.py:124`）：
> ★ 它是**按帧号重采样点搬值**（最近邻式的直接取值），★ **没有插值**。
> ★ 后果：重采样后的波形会有台阶感 / 轻微失真。★ 界面不要拿它做精细波形显示，
> ★ 它的正当用途是「按音对齐后逐位置比较幅度」——也就是它作为数据面保证存在的意义。
>
> ★ `profile.py:289-305` 记录了一个**已确认的事实**：
> ★ **当前没有任何算法消费这个端口**（pitch / dynamics 走的都是 notes.* / rms.*）。
> ★ 保留它的理由是数据面保证（算法随时能拿归一化后的 PCM 自己预处理）。
> ★ 界面若要显示它，★ 要标清楚「这是重采样后的练习侧，不用于报节奏」。

#### ⑤⑥ `pitch.reference` / `pitch.practice` — 逐帧音高曲线

```python
units="hz"  dimensions=("frame","field")
field_names=("f0_hz", "voiced", "confidence")    ★★★ 顺序即内存布局，★★★
shape=(1076, 3)  float32   hop=2048   sample_rate=44100
```

> ★★★ **订正一处：交接提纲里写的「每帧 (时间, f0, voiced)」与源码不符。★★★
> ★★★ 源码 `contract.py:187` 的 `FIELD_LAYOUTS["pitch"]` 是
> ★★★ **`("f0_hz", "voiced", "confidence")`**，★ **没有「时间」列**。★★★
> 时间不在数组里，★ 要自己按 `帧号 × 2048 / 44100` 算
> （或用 `read(port_id, (t0, t1))` 让 Core 代劳）。
> ★ 同样，★ 提纲写的「voiced」是【列 1】，★ 而提纲把 voiced 当成了最后一列。

**第 0 列 `f0_hz`** — 绝对基频，单位 **Hz**，float32。
  实测范围 `0.0 … 587.3`。
  ★ **0 表示「这一帧没发声」，不是「频率为零」**（`features.py:242-243`）。
  ★ 搜索域：`fmin=130.81 Hz`(C3) … `fmax=2093.0 Hz`(C7)，★ 故意放宽（`profile.py:158-165`）。
  ★ **绝对音高，不是 chroma** —— chroma 八度不变，用它做音准会把「低八度」判成完全正确。

**第 1 列 `voiced`** — 发声标志，float32 但**只取 0.0 或 1.0**（不是 bool）。
  判定口径：★ `confidence >= 0.5` ⇒ `voiced = 1`（**等号算发声**）（`features.py:240-241`）。
  实测：1076 帧里 1025 帧 voiced。

**第 2 列 `confidence`** — pYIN 的 `voiced_prob`，范围 **`0.0 … 1.0`**（实测），
  已被 clip 到 [0,1]，NaN→0 / +inf→1（`features.py:237-239`）。

**怎么算出来的**（`features.py:193-250` `materialize_pitch`）：
```
帧数 = 1 + (n - 2048) // 2048           （_frame_count，不足一帧按 1 帧补零）
     实测 n=2205000 → 1 + 2197952//2048 = 1076   ★ 公式与实测一致
pYIN（librosa 或自写后端，DSH_FEATURE_BACKEND 环境变量切换），
  center=True，frame_length=2048，hop_length=2048
→ f0 的 NaN/±inf 置 0
→ prob 的 NaN→0，±inf→1，clip 到 [0,1]
→ voiced = (prob >= 0.5)
→ f0 在 voiced==0 的帧上【强制置 0】   ★ 绝不让估计器的猜测值漏出去
```

> ★ **帧数 1076 vs chroma 的 1077**：两个都用 hop=2048 但公式不同
> （pitch 用 `1+(n-L)//hop`，chroma 由 librosa/native 后端的 STFT 决定）。
> ★ **差 1 帧不是 bug**，★ 但 ★ **绝不能把两条曲线按下标对齐比较**。

> ★★★ **最关键的一条实读警告 ★★★
> `profile.py:322-341` 明确记录：REFERENCE 轴**不保证两侧帧数相等**。
> 参考与练习是两段独立录音，帧数默认不同。
> ★ **本数据集的 wav 恰好全都是 72.802 秒（1568 帧），★ 把这个缺陷掩盖了。**
> ★ **换一首时长不同的练习曲即失效。**
> ★ 正确路径是 ★ **用 `notes.*` 的 `onset_sec` 按音配对后再比较**，
> ★ 这正是 `pitch` 插件实际做的（`algorithms/pitch.py:146-299`）。

#### ⑦⑧ `rms.reference` / `rms.practice` — 能量包络

```python
units="rms"  dimensions=("frame",)   field_names=()（单维，无列）
shape=(8610,)  float32   hop=256   sample_rate=44100
```

**单列** = 逐帧 **线性 RMS**（★ **不是 dB**，`features.py:259` 明文「不要在这里转 dB，
转 dB 是算法侧的表达选择」）。实测范围 `0.0 … 0.2958`。
实测 fps = 44100 / 256 = **172.3 fps**（★ 不是 100 fps，`features.py:174-176` 记录
「FILE-203:361 的『100 Hz』是陈旧残留」）。

**怎么算出来的**（`features.py:253-270` `materialize_rms`）：
```
窗长 rms_frame_length = 1024，帧移 rms_hop_length = 256（★ 比 pitch 密 8×，保留起音瞬态）
帧数 = _frame_count(n, 1024, 256) = 1 + (n - 1024) // 256
     = 1 + (2205000 - 1024) // 256 = 1 + 8609 = 8610   ★ 公式与实测一致 ★
矩形窗切帧（不足处补零）→ 每帧 sqrt(mean(x²)) → clip(0,1) → float32
```

> ★ 帧数公式统一见 `features.py:171-180` 的 `_frame_count`：
> `n_frames = 1 + (n_samples - frame_length) // hop_length`，
> ★ `n < frame_length` 时按 1 帧（补零）处理。
> ★ **三个族的帧数各不相同**（pitch 1076 / rms 8610 / chroma 1077），
> ★ **界面永远从 `manifest().ports[*].shape` 现取 shape，不要自己算。**

**★ 帧移的坑（源码反复警告）**：`ALIGN.hop_length`(=2048) 是 chroma 的帧移，
`MATERIALIZE.rms_hop_length`(=256) 是 RMS 的帧移，**两者相差 8×**。
★ 猜错**不会报错**，只会静默返回错 8× 的时刻。
→ ★ **端口自己的 `hop_length` 是唯一依据，★ 界面要自己换算时必须逐端口读。**

#### ⑨⑩ `chroma.lowres.reference` / `chroma.lowres.practice` — 12 音级色度

```python
units="chroma"  dimensions=("frame","bin")
field_names=("C","C#","D","D#","E","F","F#","G","G#","A","A#","B")
shape=(1077, 12)  float32   hop=2048   sample_rate=0
```

**12 列**，bin 顺序 ★ **从 C 开始**（★ 不是 A！★ `contract.py:203-206` 专门冻结了这一点，
因为「bin 0 是 C 还是 A」有歧义）。
每行是一帧的 12 音级能量，实测范围 `0.0 … 1.0`。

**★ 这个端口不是用来打分的。★**
`profile.py:381-385` 原文：「对齐的输入。保留在数据面里是为了**可复现**：
审查者能用它重跑对齐，验证 warp_path 不是凭空来的。**明确不作为评分依据**
（chroma 是八度不变的）」。
★ 界面若显示它，★ 必须标「不可用于评价」。
