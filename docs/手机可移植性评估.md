# 手机可移植性评估（Android / iOS）

> **方法**：只读源码 + 查已装包的版本。**没有做任何兼容性测试、没有安装任何包。**
> 下文说「能跑/不能跑」指的是**读代码得出的判断**，不是试出来的。
> 凡是需要真机才能确定的，单独列在第 5 节，不混进结论。

---

## 1 · 结论（前置）

# **判断 A —— 核心层与算法层能在手机上跑；只有「读音频」和「入口形态」要换。**

一句话理由：**`contract.py` 零平台依赖，`core/` 与 `algorithms/` 全部只依赖
numpy + scipy + 标准库，没有任何 OS 句柄、线程、信号、子进程**；真正卡住的
是 `soundfile`（要 C 库 libsndfile）与 `librosa`（要 numba/LLVM），而它们
**只出现在各自单一文件里，替换面很窄**。

```
★ 好消息（比预想好得多）
  · contract.py      只 import __future__/dataclasses/enum/numpy/types/typing
  · core/algorithms  无 threading / multiprocessing / signal / subprocess
  · algorithms/      纯 Python + numpy，★ 连 librosa 都没有
  · ★ 完全没有 torch（★ 项目早期摘要里提过它，★ 源码里一处都没有）
  · 时间用 time.perf_counter 之类，★ 不用平台时钟
```

```
★ 要换的四处
  1. soundfile  读音频      → 手机没有 libsndfile
  2. librosa   两处调用      → numba/LLVM 移动端难编译
  3. argparse  命令行参数    → 手机 GUI 不传命令行
  4. cockpit   桌面 HTTP 界面 → 那是开发调试投影，★ 手机端另做
```

## 2 · 逐层依赖实况

### `contract.py`（冻结契约）
```
__future__  dataclasses  enum  numpy  types  typing
★ 零平台依赖 ——★ 这一层可以原样搬到手机
```

### `core/`（数据面）
| 文件 | 第三方依赖 | 平台 API |
|---|---|---|
| `ingest.py` | numpy · **scipy.signal.resample_poly** · **soundfile** | `os.path`（`:48`）仅做路径判断，无句柄 |
| `align.py` | numpy · scipy（`signal.stft` `spatial.distance`） | 无 |
| `features.py` | numpy · **librosa** | 无 |
| `surface.py` | numpy | 无（`hashlib` `math` 是标准库） |
| `api.py` | numpy（间接） | `uuid`（标准库，纯计算） |

### `algorithms/`（算法面）
| 文件 | 第三方依赖 |
|---|---|
| `pitch.py` | **无 numpy**，只有 math + statistics |
| `timing.py` | numpy |
| `dynamics.py` | numpy |
| `bootstrap.py` | 无（只引 contract/profile/registry） |

★ **算法层是纯计算，★ 这一层在手机上零改动。**

### 上层（`cockpit` / `serve_ui` / `__main__`）
```
cockpit/app.py   http · socket · signal · threading · webbrowser · os
serve_ui.py      argparse
__main__.py      argparse
★ ★ 这三个是【桌面开发工具】，★ 不是数据面
★ ★ 手机端不需要它们，★ 所以 signal 只在主线程这类限制与数据面无关
```

## 3 · 四个卡点与换法

### 卡点 1 · `soundfile`（`core/ingest.py:52,89-95`）
```python
import soundfile                                   # :52
with soundfile.SoundFile(uri) as sf:               # :89
    native_sr = int(sf.samplerate)                  # :91
    data = sf.read(frames=-1, dtype="float32", always_2d=True)   # :94
```
**为什么卡**：它绑定 C 库 `libsndfile`，手机上没有现成轮子，要交叉编译。

**换法（面很窄，只这一个文件）**：
```
把「uri → (采样率, float32 数组)」抽成一个函数
★ Android：MediaExtractor / AudioTrack 取 PCM
★ iOS：AVAudioFile / AVAudioEngine 取 PCM
★ 桌面：仍走 soundfile
★ ★ 换完之后 ingest.py 里【只有这一处】需要平台分支
```

### 卡点 2 · `librosa`（`core/features.py:57`，两处调用）
```python
f0, voiced_flag, voiced_prob = librosa.pyin(...)          # :155
out = librosa.feature.chroma_stft(...)                    # :227
```
**为什么卡**：`librosa` 依赖 `numba`（LLVM JIT）与 `audioread`，移动端编译困难。

**换法**：
```
pyin        → 自己实现 YIN / pYIN（★ 纯 numpy，★ 本项目 pitch.py 已经是纯 Python）
chroma_stft → numpy 手写：STFT → 12 音级投影 → 取对数
★ ★ 两者【都只需要 numpy】，★ 而 scipy.signal.stft 已在 align.py 里用过
★ ★ 换掉后 core/features.py 就只剩 numpy
```

### 卡点 3 · `argparse`（`__main__.py` / `serve_ui.py`）
**为什么卡**：手机 GUI 不传命令行参数。

**换法**：
```
★ 数据面【完全不需要】改 ——★ 它没有 argparse
★ 只是在【进程装配层】：手机 App 用自己的参数来源（文件选择器返回值）
★ ★ 所以这不是移植障碍，★ 只是「换一种启动方式」
```

### 卡点 4 · `cockpit/`（桌面 HTTP 界面）
```
用 http.server / threading / signal / webbrowser
★ ★ 这是「契约可视图 / 调试投影」，★ 按项目定位它【本就不该上手机】
★ 手机端要另做一个界面层，★ 但它【只依赖 UiProjectionPort 两个方法】
★ ★ 而那两个方法无平台依赖 → ★ 新界面层能直接复用 core
```

## 4 · 不构成障碍的（曾被担心但实读后排除）

```
★ threading / multiprocessing  core 与 algorithms 【一处都没有】
★ signal.signal                只在 cockpit（桌面工具），★ 且已有「必须主线程」的注释
★ torch                        源码里【零引用】（★ 早期摘要提过，★ 实际没用）
★ 平台时钟                     未见 os.clock_gettime / time.clock 之类
★ 文件句柄                     ingest 只用 os.path 做存在性判断，★ 读文件走 soundfile
```

## 5 · 无法确定、需真机确认的项

以下是**读代码定不了**的，如实列出，不混进结论：

1. **`scipy` 在目标平台的可用性**
   Kivy-for-Android 与 Chaquopy 有 scipy 轮子；纯 iOS Python 方案受限。
   ★ 需要在真机上装一次才知道。**若不可用**：`resample_poly` 与 `stft`
   都能用 numpy 手写（面也很窄，两个调用点）。

2. **`numpy` 的移动端打包**
   Android 有成熟轮子；iOS 取决于选 Briefcase 还是原生嵌入。
   ★ 需按最终选型确认。

3. **`chroma_stft` 手写替换后的数值一致性**
   ★ 需与现实现对拍，★ 这是「换了之后对不对」的问题，★ 不是「能不能跑」的问题。

## 6 · 一句话总结

```
★ 数据面 + 算法面【可移植】，★ 且依赖面比预想窄
★ 要换的只有：读音频（soundfile）、两个 librosa 调用、启动方式、界面层
★ ★ 而界面层与数据面之间隔着一个无平台依赖的窄接口
★ ★ ★ 这正是当初「深组件 / 降低信息熵」那个决定的兑现处
```

★ 需真机确认的只有 3 项（第 5 节），★ 其余读代码即可定论。
