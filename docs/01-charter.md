# 项目章程

## 项目名称

口琴音频检测分析研究（harmonica-eval）

## 项目性质

**研究型项目**：先验证可行性，再谈工程化。产出以可复现的分析代码、实验结论为主，不以产品化为第一阶段目标。

## 权威边界（重要）

- **技术路线由项目负责人确定。** 本文档及仓库中任何算法选型、模型选择、特征清单、阶段划分，在负责人明确下达前一律视为**未决**。
- 交接简报中的"推荐 MVP 技术路线 / 推荐验证实验 / 推荐开发顺序"**已被删除**，不作为输入。
- 助手职责：把负责人的路线落成可运行、可复现、可测试的代码与实验，并如实报告结果。

## 待负责人裁定的事项

| # | 决策点 | 说明 |
| --- | --- | --- |
| D1 | 评价对象 | 双音频对比（标准 vs 用户）？还是单音频无参考评分？ |
| D2 | 特征范围 | 音高 / 节奏 / 力度 / 音色 / 颤音压音，取哪几维，优先级如何 |
| D3 | 时间对齐方案 | 是否做对齐；若做，用何种对齐（DTW / 音符级 / 节拍级 / 人工分段） |
| D4 | 分段方式 | 人工切段、固定时长等分、按乐句自动切分，还是由曲谱驱动 |
| D5 | 音高提取引擎 | 传统 DSP（如 pyin）还是神经网络（如 CREPE/torchcrepe），或二者对照 |
| D6 | 评分机制 | 是否给分数；若给，阈值与权重如何定；是否只用可解释规则 |
| D7 | 反馈生成 | 模板规则生成自然语言，还是引入 LLM Agent 生成 |
| D8 | 数据来源 | 真实录音优先还是合成音频先行；录音豆的采样率/格式约束 |
| D9 | 验证标准 | 什么结果算"特征能区分演奏质量"（判定指标与实验设计） |

## 交付物形态（待 D1–D9 确定后细化）

- 可复现的分析流程与实验记录
- 分析结果的可解释输出（指标 JSON + 人类可读报告）
- 结论性研究报告：哪些特征稳定、哪些不可靠、边界在哪
